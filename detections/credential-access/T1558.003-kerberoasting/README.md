# T1558.003 — Kerberoasting

| | |
|---|---|
| **ATT&CK** | [T1558.003 Steal or Forge Kerberos Tickets: Kerberoasting](https://attack.mitre.org/techniques/T1558/003/) — Credential Access |
| **Layers** | **Attempt:** one requester collects tickets for many user-account SPNs. **Effect:** the KDC issues a crackable RC4 ticket for a user-account SPN |
| **Rules** | [`correlation_win_security_kerberoasting_service_ticket_burst.yml`](rules/correlation_win_security_kerberoasting_service_ticket_burst.yml) (attempt) · [`win_security_kerberos_rc4_service_ticket_user_account.yml`](rules/win_security_kerberos_rc4_service_ticket_user_account.yml) (effect) |
| **SPL** | [`spl/`](spl/) — generated by `scripts/convert.sh`, never edited by hand |
| **Data source** | Windows Security log on every domain controller, event 4769 |
| **Status** | `experimental` — tested on public data, lab validation pending |

## Why this detection

Kerberoasting needs only a normal domain account: the attacker asks the KDC for service tickets for
SPNs that run under **user accounts**, then cracks them offline. A ticket is encrypted with a key
derived from the service account's password, so a weak password falls quickly — very quickly with
RC4, whose key is the account's NT hash.

Two changes make the usual detections age badly:

1. **RC4 is no longer the default.** With the Kerberos hardening for
   [CVE-2026-20833](https://support.microsoft.com/en-us/topic/how-to-manage-kerberos-kdc-usage-of-rc4-for-service-account-ticket-issuance-changes-related-to-cve-2026-20833-1ebcda33-720a-4da8-93c1-b0496e1910dc),
   domain controllers updated in April 2026 or later default to AES for accounts without an explicit
   `msDS-SupportedEncryptionTypes`, and the July 2026 updates remove the setting that reverted this.
   Rules that key on `TicketEncryptionType = 0x17` stop seeing a routine Kerberoast. AES tickets are
   slower to crack, but a weak password is still crackable.
2. **Filters that look like noise reduction remove real attacks.** Requiring specific
   `TicketOptions`, or dropping computer-account requesters, misses public attack captures (see the
   comparison below).

So the detection is split in two layers that fail differently:

| Layer | Question it answers | Survives AES-only domain | Main false positive |
|---|---|---|---|
| **Attempt** — burst correlation | Did one identity on one host collect tickets for many user-account SPNs? | Yes — encryption-agnostic | Admin jump hosts, multi-backend apps |
| **Effect** — RC4 ticket | Did the KDC hand out a ticket that cracks in minutes? | Fires only where RC4 is still allowed — which is itself worth knowing | Legacy services deliberately left on RC4 |

## Data sources and fields

**Audit policy:** *Account Logon → Audit Kerberos Service Ticket Operations* — **Success** on
**all** domain controllers (a DC without it is a blind spot). Failure is also worth enabling: after
RC4 removal, a downgrade attempt shows up as a failed 4769 (see *Ideas*).

| Sigma field | Event 4769 | Used for |
|---|---|---|
| `EventID` | 4769 | event type (Splunk: `EventCode`) |
| `Status` | Failure Code | `0x0` — ticket actually issued |
| `TicketEncryptionType` | Ticket Encryption Type | `0x17` RC4-HMAC, `0x18` RC4-HMAC-EXP (effect layer) |
| `ServiceName` | Service Name | exclude `*$` (computer accounts, gMSAs) and `krbtgt` |
| `TargetUserName` | Account Name | requester (correlation group) |
| `IpAddress` | Client Address | requester host (correlation group) |
| `TicketOptions` | Ticket Options | **deliberately not used** — varies by tool (see comparison) |

In Splunk the XML rendering (`XmlWinEventLog`) exposes these EventData names as fields. The CIM
Authentication data model has no ticket-encryption field, so the queries use raw fields — as ESCU
does for the same technique.

## Logic

**Effect** — `EventID=4769`, `Status=0x0`, `TicketEncryptionType in (0x17, 0x18)`, and
`ServiceName` neither ends with `$` nor equals `krbtgt`.

**Attempt** — base rule: the same filter without the encryption condition. Correlation
(`value_count`): **≥ 5 distinct `ServiceName`** per `TargetUserName` + `IpAddress` within **10
minutes**. `ServiceName` in 4769 is the account the service runs as, not the SPN string, so the
count is distinct service accounts — several SPNs on one account count once.

Design notes:

- `ServiceName|endswith: '$'` drops computer accounts and gMSAs. Their passwords are long, random
  and rotated automatically, so roasting them is pointless — that is the signal-to-noise cut.
- `krbtgt` is excluded by **exact** match. Look-alike names (`k1rbtgt`, `kr5btgt`) stay in: they
  are user accounts an attacker created, and a public capture shows them being roasted.
- The requester is **not** filtered. A Kerberoast run as SYSTEM on a compromised host requests
  tickets as the computer account (`HOST$@DOMAIN`).
- Grouping by account **and** source address separates one compromised identity on one host from
  the sum of normal activity.

## Threshold

5 distinct user-backed services in 10 minutes is a **starting point**, not a tuned value. Roasting
tools request every SPN at once (30 tickets in about 2 seconds in the Rubeus capture), while most
interactive work reaches few user-account services because most services run as computer accounts,
which are excluded. Tune it on your own baseline (*Tuning*) — the number that matters is the highest
legitimate per-requester value you observe.

What the table shows:

- **AES-only domain:** every RC4-keyed rule goes silent, including ESCU's burst search (it filters
  `TicketEncryptionType=0x17`). Only the encryption-agnostic attempt layer still fires.
- **`TicketOptions` filters miss tools.** Rubeus sent `0x40800000` for 29 of 30 tickets, so a rule
  requiring `0x40810000` sees 1. The look-alike capture uses `0x60810010`, outside both option lists.
- **Requester filters miss SYSTEM context.** Excluding `$@` requesters removes the 67-ticket capture
  entirely.
- **Cost:** the attempt layer fires on the jump host. That is the price of not keying on RC4, and the
  reason *Tuning* exists. The effect layer fires on the legacy RC4 account, as every RC4 rule does.

¹ Sigma semantics (sliding window). The generated Splunk SPL uses fixed `bin` buckets and splits
this burst 3 + 3 — see *Splunk deployment notes*.

## Known false positives

| Layer | Source | How to recognise it | Tuning |
|---|---|---|---|
| Effect | Service account explicitly set to RC4 (`msDS-SupportedEncryptionTypes` includes `0x4`) for a legacy or non-Windows client | Same `ServiceName` + same requester, every day | Fix first (enable AES, reset the password). If it must stay: allowlist the **(`ServiceName`, requester) pair**, never the `ServiceName` alone — that account is now the best roasting target in the domain, so other requesters must still alert |
| Effect | `DefaultDomainSupportedEncTypes` on a DC set to include RC4 | Many SPNs at once; KDCSVC event 205 on that DC | Configuration finding, not a tuning case |
| Effect | Before enforcement: accounts with no AES keys (password older than AES key support) | The 4769 *Available Keys* field (recent DC updates) lists RC4 only | Reset the password; after enforcement these requests fail instead of falling back to RC4 |
| Attempt | Admin jump host or tier-0 workstation touching many services | Stable source address, admin account, working hours | Allowlist the (`TargetUserName`, `IpAddress`) pair from the baseline; review quarterly |
| Attempt | Application or monitoring server connecting to many backends that run as user accounts | Same set of SPNs every run | Allowlist the pair, or raise the threshold above the observed maximum |
| Attempt | Authorised assessments | Change ticket | Time-boxed suppression |

## Possible bypasses

- **Targeted roasting** of 1–4 accounts stays under the attempt threshold; the effect layer catches
  it only if the account still allows RC4.
- **Low and slow:** spacing requests more than 10 minutes apart, or across several identities or
  hosts, splits the correlation groups.
- **AES-only requests** (`/aes` style options) in a domain that still allows RC4 bypass the effect
  layer; the attempt layer still sees a burst.
- **Kerberoasting without pre-authentication:** a service ticket obtained through an AS-REQ from an
  account with *Do not require Kerberos pre-authentication* is logged as **4768**, not 4769 — out of
  scope here.
- **Audit gaps:** a DC without *Kerberos Service Ticket Operations* auditing, or whose logs are not
  collected, is invisible to both layers.
- **Splunk-specific:** the fixed-bucket SPL (see below) misses bursts that straddle a bucket boundary.

## Splunk deployment notes

The generated queries carry no index — prefix your macro or index, e.g. `` `windows_security` ``.

**Effect** — use [`spl/win_security_kerberos_rc4_service_ticket_user_account.spl`](spl/win_security_kerberos_rc4_service_ticket_user_account.spl) as is.

**Attempt** — sigma-cli translates `timespan: 10m` into `bin _time span=10m`, i.e. fixed buckets: 6
SPNs in 3 minutes from 09:08:30 land as 3 in the 09:00 bucket and 3 in the 09:10 bucket, and the
generated search stays silent (test case *AES burst across a 10-minute boundary*). For production,
use a sliding window instead:

```spl
`windows_security` EventCode=4769 Status="0x0" NOT ServiceName IN ("*$", "krbtgt")
| streamstats time_window=10m dc(ServiceName) AS distinct_spns BY TargetUserName IpAddress
| where distinct_spns >= 5
| stats min(_time) AS firstTime max(_time) AS lastTime max(distinct_spns) AS distinct_spns
        BY TargetUserName IpAddress
```

`streamstats time_window` needs events in time order; the default reverse-chronological order of
search results qualifies. This variant is hand-written and **not yet validated in Splunk** — see the
lab validation below. Schedule it every 5 minutes over the last 15 minutes and throttle on
`TargetUserName, IpAddress`.

## Tuning

Run on at least 30 days of data before enabling.

**Attempt — what is normal per requester?**

```spl
`windows_security` EventCode=4769 Status="0x0" NOT ServiceName IN ("*$", "krbtgt") earliest=-30d
| bin _time span=10m
| stats dc(ServiceName) AS spns BY _time TargetUserName IpAddress
| stats count AS windows max(spns) AS max_spns perc99(spns) AS p99_spns BY TargetUserName IpAddress
| where max_spns >= 3
| sort - max_spns
```

Every row at or above the threshold is either an allowlist candidate (known host, known account,
explainable) or something to investigate. Keep the threshold above the highest *legitimate*
`max_spns`, not above the average.

**Effect — which SPNs still get RC4?**

```spl
`windows_security` EventCode=4769 Status="0x0" TicketEncryptionType IN ("0x17", "0x18")
  NOT ServiceName IN ("*$", "krbtgt") earliest=-30d
| stats count dc(TargetUserName) AS requesters values(IpAddress) AS sources BY ServiceName
| sort - requesters
```

Each `ServiceName` here is a remediation item first and an allowlist entry only if it cannot be
fixed.

## Ideas

- **Downgrade attempt layer.** Roasting tools typically advertise only RC4 to get a fast-to-crack
  ticket. Against an AES-only service, after enforcement, that request fails: 4769 with failure code
  `0xE` (`KDC_ERR_ETYPE_NOTSUPP`) and KDCSVC events 203/208 in the System log. Modern Windows clients
  advertise AES, so an RC4-only request from a Windows host is suspicious. Needs lab data first.
- **New 4769 fields** on Windows Server 2025 (*Advertized Etypes* — what the client asked for)
  would let the effect layer distinguish "client asked for RC4" from "account only has RC4".
- **Risk-based alerting:** emit both layers as risk events on the requester; let the combination
  (burst + RC4 effect, or burst + downgrade failures) raise the notable.
